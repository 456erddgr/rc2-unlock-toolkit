# 技术记录：RC2 是怎么被攻下来的

本文记录逆向过程和踩过的坑。**包含失败的部分** —— 这部分比成功的部分更有参考价值。

> 📌 **实际交付的主线是 Root ADB**（`ADB-Unlock-RC.exe` + `Root-ADB.exe`）。本文的 §2 讲的是「root shell 从哪来」这个问题的探索过程，§3 之后讲的是工具箱用到的手法。想直接上手看 [README](../README.md) 和 [安装与使用指南](安装与使用指南.md)。

## 1. 设备概况

| 项目 | 值 |
|---|---|
| 型号 | DJI RC2 带屏遥控器 |
| 内部代号 | **KATMAI-IDP** |
| 平台 / 板级 | `rc331` |
| SoC | Qualcomm **QCS5430**（lahaina） |
| 系统 | Android 11（SDK 30） |
| 内核 | `5.4.210-qgki` |
| CPU | Cortex-A55，**运行在 32 位 armv8l** |
| 内存 | 1.75 GB |
| 固件 | V00.01.12.50 |
| 指纹 | `DJI/rc331/rc331:11/V00.01.12.50/11250:user/test-keys` |
| 系统签名 | **test-keys** |

**两个关键点：**

1. **32 位。** 不是 arm64。所有 64 位 native 库和 arm64-only 的 APK 都用不了。
2. **test-keys。** 系统用的是测试签名，不是正式发布签名。这意味着系统对 APK 签名的校验宽松得多 —— 很多「正常设备上不可能」的操作在这里可行。

## 2. 攻击面

### 2.1 免认证的 adbd

RC2 的 adbd 监听在 `127.0.0.1:5555`，**免认证**。

```
VID:PID 对照
  2ca3:1021   正常模式
  18d1:4ee7   ADB 模式
  05c6:901d   DIAG 模式
```

只要能触发 ADB 模式（或让设备自己把 adbd 拉起来），就能直接连进去，不需要点授权。

### 2.2 `djilink` 的 Binder 注入（真正的突破口）

固件里有个叫 `djilink` 的服务，是工厂测试用的 Binder 服务。

它的 `setMicStatus(...)` 方法会把参数拼进 shell 字符串执行：

```c
tinycap %s -D 0 -d 0 -i %d -c %d -r 48000 -b 16 -t %d
```

**第一个 `%s`（录音文件名）没有任何过滤**，直接来自 Binder parcel。用 `;` 就能注入任意命令：

```bash
service call djilink 1030 i32 1 i32 1 i32 2 i32 1 s16 ";whoami > /sdcard/whoami;"
```

参数细节：

| 项 | 值 |
|---|---|
| 服务名 | `djilink` |
| 事务码 | `1030`（`0x406`） |
| 参数签名 | 4 × `i32` + 1 × `s16` |
| 长度限制 | 整条命令 < 128 字符 |

这是整条链子的起点。拿到命令执行之后，剩下的都是常规 Android 提权套路。

### 2.3 从命令执行到 root

拿到 `djilink` 的命令执行后（此时已经是 `shell` 或更高），用 `am attach-agent` 把脚本注入 `system_server`：

```
adb-root-launcher  (setuid 4755)
    └─> /data/adb-persist/start-root-adbd.sh
            └─> am attach-agent system  ──注入──>  system_server
                    └─> 干掉原版 adbd
                    └─> 起 adbd-root --root_seclabel=u:r:su:s0
```

`sadb-root-launcher` 被设了 **setuid 4755**，所以任何 App 都能调用它来触发这条链子。

最终得到一个跑在 `u:r:su:s0` 上下文里的 adbd，这在 SELinux 策略里是**非受限域**。

## 3. `su` 怎么进 PATH（最巧的一步）

### 问题

`/system`、`/product`、`/vendor` 都是 **dm-verity 只读分区**：

```bash
$ mkdir /system/xbin
mkdir: '/system/xbin': Read-only file system
```

rootfs 也 `remount,rw` 不动。传统 Magisk 那套「往 `/system/xbin` 丢 su」在这里完全行不通。

### 观察

应用进程的实际 PATH：

```
/product/bin:/apex/com.android.runtime/bin:/apex/com.android.art/bin:/system_ext/bin:/system/bin
```

头一项是 `/product/bin`，而它**只装了一个文件**：

```bash
$ ls -la /product/bin/
-rwxr-xr-x 1 root shell 1400 init.qti.display.sh
```

### 方案

```bash
D=/product/bin
B=/data/adb/ksu/.orig-product-bin

# 1. 记下原文件
cp -a "$D"/. "$B"/

# 2. 用 tmpfs 盖住
mount -t tmpfs -o mode=0755 tmpfs "$D"

# 3. 把原文件放回去（原件仍可见！）
cp -a "$B"/. "$D"/

# 4. 放 su
cp /data/adb/ksu/bin/su "$D/su"
chmod 0755 "$D/su"
```

### 为什么这样可行

- tmpfs 挂上去之后，`/proc/<pid>/mounts` 里所有进程都能看到这一条
- **zygote 也能看到**，所以之后新起的进程同样看得到
- 代价极小：只遮蔽了一个 **1.4 KB** 的脚本，而且原件仍然可见
- **重启后 tmpfs 消失，`/product/bin` 自动恢复原样，不留任何痕迹**

因为 tmpfs 是内存态，重启会丢，所以加了个开机自愈：

```
/data/adb/ksu/.nexus_pathsu   ← 持久标记，用来区分「该不该自动补挂」
/data/adb/ksu/nexus-boot.log  ← 持久日志（logcat 关机即失，这个留着事后追查）
```

标记文件的作用是防止「用户关机时是开着的，开机后凭空多出一个 tmpfs」这种意外。

## 4. `su` 前端

写了个 KernelSU / Magisk 兼容的 shell 前端：

```bash
su -c "命令"       # 支持管道、引号、分号原样透传
su -v /su -V /su --version
```

实现上走的是广播桥：

```
[App] --广播--> SuReceiver --> /data/local/tmp/nexus-su/req.PID
                                     |
                              [root adbd] 执行
                                     |
                            out.PID / out.PID.rc  <-- 结果回传
```

`/data/local/tmp/nexus-su` 被挂成 `mode=0777` 的 tmpfs，保证 App 能写请求文件、能读结果文件。

另外做了个 `ksud` shim，让探测 KernelSU 的脚本能找到「真的东西」：

```bash
ksud --version      → 4.6
ksud su ...         → 转发给真的 su
ksud module list    → ls /data/adb/modules
ksud module install → nexus-module-install
```

## 5. 内核补丁：诚实的失败

**这是整个项目最应该被记住的一节。**

### 结论

**做不到。** RC2 内核 `5.4.210-qgki` 里**没有 KernelSU 的代码**。

KernelSU 由两部分组成：
- **用户态**：App + `ksud` CLI —— 可以装
- **内核态**：LKM 或内核内建 —— **没法从用户态凭空变出来**

KernelSU 官方 App 装得上，但打开会显示「未安装」—— 因为内核那一半根本不存在。

### 工具箱里的「内核补丁」到底做了什么

它**不会**帮你刷内核。它做了一件诚实的事：

| 步骤 | 动作 | 是否写盘 |
|---|---|---|
| 1/6 | 从内置管理器 APK 提取官方 `ksud` 和 `magiskboot` | 写 `/data/adb/ksu/bin` |
| 2/6 | 只读盘点内核 / boot 分区 / LKM 支持 | 只读 |
| 3/6 | 搜 `.ko` 文件，有就尝试加载 | 只读 |
| 4/6 | dump 真实 boot 镜像 | 写 `/sdcard/RC2NEXUS` |
| 5/6 | 交给 `ksud boot-patch` 处理 | 写输出文件 |
| 6/6 | **原样报告每一步的真实输出** | — |

**它从头到尾不写块设备。**

### 为什么不写块设备

因为 **`fastboot flash` / `erase` 这类写操作没有安全边界**。手机刷错 boot 还能重刷，RC2 上写错分区可能真的回不来。

检查项：

```bash
# 内核
uname -r
cat /proc/cmdline
cat /proc/version

# 有没有 KSU
ls /sys/module | grep -i -e ksu -e kernelsu
grep -i -e kernelsu -e ksu /proc/kallsyms | head -5

# LKM 支持
grep -w module /proc/filesystems
cat /proc/sys/kernel/modules_disabled

# .ko 文件
find /data/adb /data/local/tmp /sdcard -maxdepth 4 -name '*.ko' 2>/dev/null | head -20

# boot 分区
ls -l /dev/block/by-name/ | grep -i -e boot -e init_boot -e recovery
cat /proc/partitions
```

**宁可少一个功能，也不做不可逆的操作。**

## 6. DJI 隐藏的工厂组件

| 包名 | 用途 | 备注 |
|---|---|---|
| `com.dpad.fuli` | 开发助手 | 工厂调试用 |

## 7. 本项目的边界：为什么整条链路是安全的

这一节值得单独写，因为网上讲 DJI 破解的内容几乎都在讲**刷机**，看到"破解遥控器"很容易以为本项目也一样。**本项目走的是完全不同的路线。**

### 与刷机路线的对比

| | 网上常见的刷机路线 | **本项目** |
|---|---|---|
| root 来源 | 解锁 BL → 刷 Magisk 补丁 boot | **出厂的 root adbd**（uid=0，`127.0.0.1:5555`） |
| 需要解 BL 吗 | 需要 | **不需要** |
| 会烧 eFuse 吗 | 解锁时烧，不可逆 | **不会**，全程不碰 `flashing unlock` |
| 写块设备吗 | 写 boot 分区 | **不写**，`fastboot flash`/`erase` 一个都不用 |
| 动系统分区吗 | 改 `/system` 等 | **一个字节都不动** |
| 能还原吗 | 难以完全还原 | **关开关/恢复出厂即回到原样** |
| 有变砖路径吗 | 刷错 boot 就砖 | **没有**，不写分区就没有砖的路径 |

### 机制上为什么不碰分区

root 是通过 `am attach-agent system` 注入拿到的（见 §1），注入对象是**运行中的进程**，不是存储介质。`su` 入口只落在两个位置：

```
/data/adb/ksu/          ← su 二进制与白名单
/data/local/tmp/        ← 注入脚本与 spool
```

这两个都在 `/data` 下，**属于用户数据区**，与系统分区无关。所以：

- 关掉「临时 root」开关 → 入口删除，白名单清空
- 恢复出厂设置 → `/data` 被格式化，一切归零
- 系统分区从始至终未被写入

### 关于 fastboot

App 里有一个 **Fastboot 面板**，但它只做救援，不做写入：

```bash
fastboot devices          # 认设备
fastboot getvar product   # 确认型号（应为 rc331）
fastboot continue         # 继续正常启动（推荐）
fastboot reboot           # 重启
```

**这些是安全的。** 面板不提供、项目也不引导你使用下面这些写操作：

```bash
fastboot flash ...        # 写分区
fastboot erase ...        # 擦分区
fastboot flashing unlock  # 会烧 efuse，不可逆
```

### 开发机的情况

开发机在一次 **DJI Fly 自动更新**后没能正常启动，落到了 fastboot 模式。

**这不是变砖**：`fastboot devices` 能认到设备、bootloader 响应正常，`fastboot continue` 即可继续启动。设备本身没坏。

原因推测：DJI Fly 更新后会重新校验安全启动链，检测到运行环境被改动过（TEE 校验失效），于是拒绝正常引导。**这一条是推断，不是抓到的实证。**

需要强调的是：**这是 DJI Fly 升级行为导致的，不是本工具造成的。** 本工具没有写任何分区，也没有留下需要刷机才能清除的痕迹。

### 判断当前设备状态

| 现象 | 判断 | 怎么办 |
|---|---|---|
| `fastboot devices` 能认到机器 | **设备是活的**，bootloader 正常 | `fastboot continue` 或 `fastboot reboot` |
| 停在 boot logo，但 `adb devices` 有反应 | 系统在跑 | 排查 ADB / 应用层问题 |
| `fastboot` 和 `adb` 都毫无反应 | 才需要物理手段 | 拆机进 EDL 9008，或返厂 |

### 经验

> **Root 之后建议不要更新 DJI Fly** —— 这是经验之谈，不是本工具的副作用。
>
> 以及：**解锁 Bootloader 会永久烧掉熔丝位**（不可逆），而本项目完全不需要解锁 —— root 入口是出厂自带的。
>
> 还有：**按不动的时候先确认设备在哪一层**。能进 fastboot 就有救，别把能救的情况当成救不回来。

## 8. 复现路径总结

想从头理解这条链子，按这个顺序看：

```
1. ONLINE-TEMPROOT 记录  →  djilink Binder 注入（起点）
2. RootAdb.java          →  root adbd 持久化
3. TempRoot.java         →  临时通道
4. KsuActivity.java      →  su / 白名单 / PATH 注入 / 模块
5. SuProvider.java       →  su 前端实现
6. SuReceiver.java       →  广播桥
7. SysProp.java          →  resetprop（不需要内核模块的能力）
```

## 9. 未解决的问题

- **内核态 root 仍然不可行。** 除非找到可加载的 LKM，或者有办法解锁并刷入自定义内核。
- **设备的当前状态停在 fastboot 模式，尚未恢复到正常启动。** 已确认 bootloader 正常、可以进入 fastboot，不是变砖；下一步是确定 DJI Fly 更新到底改了什么导致引导被拒。
- **DJI Fly 的检测逻辑只推测了机制，没有实证。** TEE 校验失效这条是推断，不是抓到的。
- **未做 Bootloader 解锁路径的探索。** 本项目全程不需要解锁 BL（root 入口是出厂自带的），所以也没有尝试过、没有记录过解锁步骤。

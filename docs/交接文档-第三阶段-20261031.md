## 十、第五阶段 v2.1-v2.5 重大修复（2026-10-31 09:00-09:47）

### 10.1 ⚠️ 重大纠错：pwm3 是屏幕背光，不是风扇！
交接文档 §五 写"风扇：/sys/class/pwm/pwmchip0/pwm3"是**错的**，踩了大坑（调它导致屏幕闪/黑屏，unexport 后直接黑屏）。

| 芯片 | 通道 | 真实用途 |
|---|---|---|
| pwmchip0 | ch3 | **屏幕背光**（调它=调亮度；unexport=黑屏！） |
| pwmchip4 | ch0 | 风扇（**被内核 pwm-fan 驱动独占**，export 返回 1） |

**黑屏恢复方法（务必记住）**：
```sh
su -c "echo 3 > /sys/class/pwm/pwmchip0/export; \
echo 1000000 > /sys/class/pwm/pwmchip0/pwm3/period; \
echo 1000000 > /sys/class/pwm/pwmchip0/pwm3/duty_cycle; \
echo 1 > /sys/class/pwm/pwmchip0/pwm3/enable; \
echo 255 > /sys/class/backlight/panel0-backlight/brightness"
```

### 10.2 风扇真相（已彻底查明）
- 风扇设备：`/sys/devices/platform/soc/soc:pwm-fan`，supplier=pm8350c pinctrl@8800，`waiting_for_supplier=0`（已绑定内核驱动）
- **cooling_device 0-22 里没有任何 fan 类型**（全是 thermal-cpufreq/cpu-hotplug/cpu-isolate/devfreq/backlight/icnss）
- `pwmchip4` export ch0 → **返回 1**（内核占用，用户空间无法操作）
- **结论：风扇由内核 thermal-engine 自动调速，App 无法直接设占空比**
- DJI 内部应用 `com.dpad.devicetest`（开发助手，userId=1000）里有 `SystemFanTestActivity`，其 dex 里的 `doSetFan/enableFan/closeFan/getFanSpeeds/SYS_FAN_CTRL/sys.fan.actual_speed` 全部走 **`android.hardware.thermal` HIDL**（IThermal V1.0/V2.0），而非直接 pwm —— 但 HAL 侧也不暴露 fan cooling device
- 工具箱 v2.5 风扇页**如实显示**：转速=内核自动、CPU/电池温度、最热传感器、驱动绑定状态 + 温度联动建议

## 十五、第十阶段 ⚠️ 开机死机根因修复（2026-10-31 11:39-11:55）★最关键★

### 15.1 故障现象
用户报告：**遥控器开机 56 秒后卡顿，直到死机卡在页面动不了**（约 1 分钟）。同时软件内「虚拟内存关闭后无法再开启，点击开启就卡死」。

### 15.2 根因（两个，都致命）

**根因 A：swap 文件开机重建要 89 秒，但设备 56 秒就死了**
开机日志实锤：
```
11:38:36 开始创建 2046MB swap 文件
11:40:05 文件创建完成   ← 耗时 89 秒！
11:40:07 启用成功
```
- `service.sh` 是 `sleep 60` 后才开始检查，若大小不符就**重建**（分块 dd 2046MB）
- 但设备在 **56 秒**时就因内存耗尽死机 —— **永远等不到 swap 建好**
- 更糟：文件常是半截（卡死中断），下次开机又判"大小不符"又重建 → **死循环**

**根因 B：size_mb 配置与实际文件差 2MB，永远判为"不符"**
- 实际文件：`2147483648` 字节（=2048MB）
- 配置 size_mb：`2046` → 期望 `2145386496` 字节
- **差 2097152 字节（2MB）** → 每次开机都判不符 → 每次重建 → 每次都死

**根因 C：App 内"开启 swap"调 swapctl.sh on（会触发 89 秒重建）**
- `doEnable` → `swapctl.sh on` → 大小不符就重建 89 秒 → 超出 `LONG_TIMEOUT_SEC` → UI 假死
- 用户看到的就是"点击开启就卡死"

### 15.3 修复（三层）

**① `module_swap/service.sh` 重写为 v3「预建文件，开机只 swapon」**
```sh
sleep 8                        # 从 60 秒改 8 秒，尽早就绪
# 文件大小正确 → 直接 swapon（<1秒）
# 文件大小不符 → 不重建！只记警告（重建必须手动触发）
```
效果：**swap 15 秒内就绪**（原来要 89 秒）

**② 修正 `size_mb`：2046 → 2048**，与实际文件字节数完全匹配

**③ `SwapPage.doEnable` 改为纯 swapon（不重建）**
```java
long want = sizeMb * 1048576;
long cur  = stat /data/local/rc2_swapfile;
if (cur != want) return false;        // 明确失败，不卡死
/system/bin/swapon -p 32767 ...       // 秒级
```
`doDisable` = 纯 swapoff；只有 `doResize`（点"应用容量"）才重建，并有明确 toast 提示"需 1-2 分钟"

**④ 内存优化**
- `statusTick` 5 秒 → 8 秒（减少刷新开销）
- `BootAnimPage` 帧数 48 → 20（1080×1920 × 48 帧约吃 400MB，1.7GB 设备扛不住）

## 二十四、关键铁律总表（踩坑血泪，务必遵守）

## 二十七、开机动画「只抽 18 帧 → 看不到动画」根因与修复

### 27.1 根因（四个叠加，不是单一原因）
| # | 位置 | 问题 |
|---|---|---|
| 1 | `framesFromVideo()` | `int frames = Math.min(20, Math.max(6, durMs/250))` —— **上限焊死 20 帧**，4.48 秒视频算出 17~18 帧 |
| 2 | `mmr.getFrameAtTime(us, OPTION_CLOSEST_SYNC)` | 只抓**关键帧**。实测该视频 `stss` 只有 1 个关键帧（第1帧），关键帧稀疏 → 大量重复帧 |
| 3 | `desc.txt` 写死 `"24"` | 不区分播放速度，且**帧数少 × 24fps = 播放不到 1 秒**，看着像没播 |
| 4 | 所有帧 `Bitmap` 攒在 `List` 里 | 1920×1080 ARGB ≈ 8MB/帧，48 帧 ≈ 380MB → 1.7GB 设备 OOM 被杀，zip 是残的 |

### 27.2 修复（`BootAnimPage.java` 重写为 v3）
1. **帧数做成滑块由用户定**：12 ~ 120 帧
2. **播放速度做成滑块**：10 ~ 30 fps
3. **新增「同步原时长」模式**（默认）：`帧数 = ⌈视频秒数 × fps⌉`，动画时长 = 视频时长
   - 实测 4.48 秒 @24fps → **109 帧 → 播放 4.54 秒**（与原视频一致）
   - 超长视频有 `MAX_SYNC_FRAMES=360` 保护，超限时自动降 fps 以保持时长一致
4. **边取帧边写 zip（流式）**：内存峰值 = 1 帧（约 8MB），彻底解决 OOM
   - 新增内部类 `ZipWriter`，每帧 `compress → writeStored → recycle`
5. **取帧改 `grabFrame()`**：优先 `getScaledFrameAtTime(OPTION_CLOSEST)`（直接解码到目标尺寸，省内存且更准），失败回落 `getFrameAtTime`
6. **居中均匀采样**：`us = (i + 0.5) / frames × durMs`，避免首末帧时间点重合
7. **尾部保护**：末帧采样点限制在 96% 处（实测末端 seek 会回退成首帧）

## 二十八、虚拟内存「关不掉」根因与修复

### 28.1 根因
| # | 问题 |
|---|---|
| 1 | `doDisable()` 走 `sh swapctl.sh off` —— toybox `swapoff` 对 2GB 文件常报 `Invalid argument`，脚本还有重试/等待 → UI 假死 |
| 2 | 判定条件过严：`ok = !diskLeft && !fileLeft && marked` —— 任一环境差异（如文件已被删）就永远报失败 |
| 3 | `doEnable()` 文件不存在/大小不符时**直接 return false** —— 而「关闭」会把文件删掉，导致**关了再也开不回来** |
| 4 | `service.sh` 里 `PRIORITY=32767`（高于 zram 32758）违反铁律4；`swappiness 150` 超内核上限 100 |

**`SwapPage.java`**
- `doDisable()` 改为纯本地逻辑，完全不调 `swapctl.sh`：
  1. `swapoff`（失败不致命）→ 若仍活跃，把 swappiness 提到 100 并等 1.5 秒再重试一次
  2. 写 `disable` 标记（**关键**：阻止开机 service.sh 重建 2GB 文件，历史「开机56秒死机」就是它）

- `doEnable()` 改为**幂等 + 自动重建**：
  - 已在跑 → 直接返回成功
  - 文件不存在/大小不符 → 调 `swapctl.sh resize` 自动重建（沿用已修好的分块 dd + sync）

- 新增 `ensureShell()` / `shellExec()`：只启**一个**常驻 `su -c sh` 进程，
  命令走 stdin 管道，回读用哨兵行 `__RC2_EOF__` 分隔，单条降到 5-20ms。
- `exec()` 在 ROOT 模式优先走常驻会话；失败自动回退到原「起进程」方式（保证兼容）。
- **常驻会话用独立 `SHELL_LOCK`，不复用 `LOCK`** —— 否则所有页面会互相阻塞。
